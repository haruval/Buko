# Buko: pre-device security and data-safety review

Reviewed September 10, 2026, against the current working tree, including page spacing, the page library, recoverable page deletion, and Empty Trash.

**Assessment:** reasonable to test on your iPad with disposable notes. No app-code behavior indicating device compromise, data exfiltration, or modification of other apps was found. This is a source/configuration review and simulator validation, not a guarantee of zero risk or a penetration test of iPadOS.

## Findings addressed

- **Concurrent windows could overwrite a note.** Each PencilKit canvas saves a complete drawing, and existing views do not merge another window's edits. The generated app manifest previously enabled multiple scenes. Added `Configuration/Info.plist` and disabled manifest autogeneration so the final built app explicitly declares `UIApplicationSupportsMultipleScenes = false`. Multi-window editing should return only with conflict handling. This risk was identified from the data flow; a two-window overwrite was not deliberately performed on user notes.
- **Failed drawing loads needed stronger write isolation.** Disabling touch input alone did not prevent potential programmatic drawing callbacks from an empty fallback canvas. `NoteCanvas` now attaches the writer, tool-session canvas, and page persistence callback only after successful decoding. Its drawing delegate also rejects callbacks before a successful load. Original drawing bytes remain untouched on failure. Build-checked and reviewed. Corrupted archived-page decoding is now fault-tested; full corrupt-store recovery remains a separate integration case.

## Security scope and evidence

- Reviewed the shipping Swift files, persistence paths, project build configuration, generated simulator Info.plist, and linked app libraries. The app uses Apple frameworks; no third-party package dependencies, embedded service credentials, custom build scripts, dynamic code loading, web views, network client/server, analytics, or AI requests were found.
- No camera, microphone, photos, contacts, location, local-network, or tracking access is implemented or requested. No background execution modes, document import handlers, URL schemes, file-sharing settings, app groups, or iCloud entitlements are configured in this project.
- Notes are written through SwiftData in the app container. Preferences use AppStorage. The shipping app contains no filesystem deletion routine. Note deletion and page deletion first move records to Trash. Empty Trash permanently deletes only specifically captured, revalidated SwiftData trash records after an in-app confirmation. Test-only temporary-store cleanup is outside the app target.
- Storage initialization failures preserve existing files instead of deleting/recreating the database. Save errors are shown with a retry action. Appearance changes preserve stroke geometry and save canonical monochrome ink.
- On a normally configured iPad, third-party apps run in Apple's sandbox, which restricts access to other apps and system files. This is an OS security boundary, not a promise that software has no bugs. [Apple's sandbox and entitlement documentation](https://support.apple.com/en-ae/guide/security/sec15bfe098e/web).

## Remaining risks and limits

1. **Buko is not yet a safe sole copy of important notes.** There is no export, independent backup, version history, or sync. Deleting the app, storage corruption, a future migration bug, or device loss can lose its local notes. Trash does not protect against those events. System backups depend on the user's device settings and are outside this app's backup guarantees.
2. **Recent edits can be lost on abrupt termination.** Explicit saves wait for 500 ms of inactivity, and note switching/scene deactivation flush changes. A crash during continuous writing, an in-flight stroke, or failed storage writes can lose edits since the last successful save. It is not a strict 500 ms maximum loss window.
3. **Large-note performance is not yet characterized on hardware.** Drawing serialization and snapshots have main-thread work; rapid gestures can overlap background Gaussian rendering jobs. Raster dimensions are capped, but stroke count, note count, and document length are not. Heavy usage may cause lag, battery use, memory pressure, or an app termination. No code that disables device thermal protections or performs privileged hardware operations was found.
4. **No private-note lock.** The app relies on device security and default OS file protection; it does not implement its own encryption or Face ID lock. Open notes may be visible in the app switcher. Exact on-device file protection and the final development-signed entitlements were not measured in this simulator review.

Installed and launched on the existing iPad Pro 13-inch (M5) simulator running iPadOS 27. A screenshot confirmed the workspace, existing note entries, and removal of the selected-note dot. Physical M4 deployment was not performed.

## Page-library deletion review

- **Scope:** `NotebookEdits.emptyTrash` operates on Note/TrashedPage model IDs, never paths or URLs. Active notes are protected even if their IDs appear in an old confirmation snapshot. Restored pages are absent from the archive query and cannot be removed by that snapshot. It does not call FileManager removal, reset a store, bulk-delete all notes, invoke a shell, or access another app's data. There are no cascading relationships.
- **Atomicity:** pending edits are saved before structural operations. Autosave is suspended during the operation, and ink, page metadata, and archive insertion/removal commit together. Errors roll back the context and explicitly restore affected notes' live property values. This extra restoration addresses observed SwiftData rollback caching behavior. If saving still fails, original values remain available for Retry.
- **Ink preservation:** page spacing migrates existing strokes by a vertical translation only, once per notebook layout version. Points, pressure, transforms other than the intended translation, and stroke seeds are retained. Deleting a page archives complete strokes owned by their starting page; paths crossing a boundary are not cropped or discarded. Restoration reverses page shifting. Stable page IDs and retained order markers support restoration in any order, including after deleting all pages. Empty notebooks remain empty until a page is added or restored.
- **Callback isolation:** structural edits invalidate the old canvas revision before stopping its camera. Late old-canvas drawing/page callbacks cannot overwrite the edited notebook. Operations that switch notes or remove pages require the current drawing stroke to finish first.
- **Test evidence:** an actual pre-change SwiftData schema/store was opened by the new model and migrated. Checks cover idempotent migration, complete stroke preservation, multiple deletions and out-of-order restoration, blank/last-page deletion, rollback after staged soft and permanent deletion, active-note and active-page preservation, stale confirmations, corrupted archive protection, and preservation of an unrelated sentinel file. All passed on isolated temporary data. No real iPad Trash was emptied during testing.
- **UI/build evidence:** the normal simulator build passed. Separate simulator UI tests passed for thumbnail navigation, rename/delete/restore, Empty Trash cancel/confirm, last-page restoration, relaunch persistence, and title-pill width. Installed and launched the final build on the existing iPad Pro simulator without uninstalling or emptying its Trash; the page-progress control is visible on the existing notebook.
- **Limits:** Empty Trash intentionally destroys Buko content and cannot be undone. The existing backup/export, abrupt-termination, and hardware-performance limitations above still apply. This implementation limits its actions; it does not establish that bugs or device/storage failures are impossible.
